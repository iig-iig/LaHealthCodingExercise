2. SCENARIO
==================================================

An online member registration is submitted to a CRM.

The integration receives the CRM registration as JSON, validates it, and transforms it into the JSON contract expected by a legacy membership REST API.

For this exercise, do NOT actually call the legacy API.

The Azure Function should return the transformed legacy payload.

==================================================
3. INPUT CONTRACT
==================================================

Example request:

{
  "firstName": "Alex",
  "lastName": "Nguyen",
  "dateOfBirth": "1990-04-12",
  "email": "alex.nguyen@example.com",
  "membershipType": "Single",
  "registeredAt": "2026-06-01T09:00:00Z"
}

registeredAt is optional for this exercise.

If supplied:
- accept it;
- do not validate it;
- do not map it;
- do not include it in the legacy payload.

Unexpected additional JSON properties must be ignored and must not cause deserialization or validation to fail.

==================================================
4. EXPECTED OUTPUT
==================================================

For the example request, return:

{
  "member": {
    "given_name": "Alex",
    "family_name": "Nguyen",
    "dob": "12/04/1990",
    "contact": {
      "email": "alex.nguyen@example.com"
    },
    "plan_code": "S",
    "source": "MILKYWAY"
  }
}

The JSON property names in the output must match this contract exactly.

Use JsonPropertyName attributes where appropriate so that the legacy snake_case property names are explicit and deterministic.

==================================================
5. MAPPING RULES
==================================================

Map:

firstName
-> member.given_name

lastName
-> member.family_name

dateOfBirth
-> member.dob

email
-> member.contact.email

membershipType
-> member.plan_code

source
-> always the literal "MILKYWAY"

Do not include registeredAt in the legacy response.

==================================================
6. PLAN CODE MAPPING
==================================================

Use the following mapping:

Single -> S
Family -> F
Couple -> C

Treat these values as case-sensitive using ordinal comparison.

Therefore:

"Single" = valid
"Family" = valid
"Couple" = valid

But values such as:

"single"
"FAMILY"
"couple"
"Couples"

must be rejected.

Do not silently normalize unsupported values.

==================================================
7. DATE HANDLING
==================================================

dateOfBirth must be provided in exactly:

yyyy-MM-dd

Example:

1990-04-12

The legacy system requires:

dd/MM/yyyy

Example:

12/04/1990

Validate the date using:

DateOnly.TryParseExact

with:

"yyyy-MM-dd"
CultureInfo.InvariantCulture
DateTimeStyles.None

Do NOT use:
- DateTime.Parse;
- DateTime.TryParse without an exact format;
- current machine culture;
- manual substring manipulation.

The date must also represent a real calendar date.

For example:

1990-02-30

must be rejected.

Format the resulting legacy date using:

"dd/MM/yyyy"

and CultureInfo.InvariantCulture.

==================================================
8. VALIDATION
==================================================

Validation must occur BEFORE mapping.

The following properties are required:

- firstName
- lastName
- dateOfBirth
- email
- membershipType

Treat all of the following as missing:

- property absent;
- null;
- empty string;
- whitespace-only string.

Validate:

1. firstName is required.
2. lastName is required.
3. dateOfBirth is required.
4. dateOfBirth must be exactly yyyy-MM-dd and represent a valid calendar date.
5. email is required.
6. email must have a plausible email format.
7. membershipType is required.
8. membershipType must be exactly Single, Family, or Couple.

A missing field must not also produce a format validation error.

For example:

"email": ""

should produce:

"email is required"

and NOT also:

"email is invalid"

==================================================
9. EXACT VALIDATION MESSAGES
==================================================

Use these exact messages:

"firstName is required"

"lastName is required"

"dateOfBirth is required"

"dateOfBirth must be in yyyy-MM-dd format"

Return ALL applicable validation errors in a single response.

3. dateOfBirth
4. email
5. membershipType

11. MALFORMED REQUEST HANDLING
==================================================

The Function must gracefully handle:

- empty request body;
- malformed JSON;
- JSON null;

- missing fields;
- invalid fields;
- unexpected extra properties.

Return HTTP 400 for invalid request JSON.

Use a clear error such as:

For an empty body, return a clear validation response, for example:

  ]
}

Do not expose:

- internal server information.

13. ERROR HANDLING
==================================================

Handle expected failures explicitly:

- empty request;
- malformed JSON;
- validation failures.
